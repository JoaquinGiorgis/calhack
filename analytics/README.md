# FortWatch analytics

A live web dashboard of every alert FortWatch sends, built on
[SpacetimeDB](https://spacetimedb.com).

```
mac_listener.py ──HTTPS POST──► SpacetimeDB (module in spacetimedb/) ──WebSocket subscription──► dashboard/
  alert name, YAMNet score,        stores alerts + hourly rollups              updates within ~1 s,
  0-100 mic level, wristband       on the server                               no polling
  connected?
```

**Privacy:** only what the wristband already receives is uploaded: the alert name, its
YAMNet score, the 0-100 level, and whether the wristband was connected. **No audio,
no transcripts.** Analytics is **off** unless you configure it.

## What's here

| Path | What it is |
|---|---|
| `spacetimedb/src/index.ts` | SpacetimeDB module (TypeScript): tables, HTTP ingest, demo simulator |
| `dashboard/index.html` · `app.jsx` | The dashboard (React + ECharts + SpacetimeDB SDK). `app.js` is built from `app.jsx` |
| `dashboard/module_bindings/` | Client bindings generated by `spacetime generate` |
| `../live_demo/mac_listener.py` | Uploads alerts when `FORTWATCH_ANALYTICS_URL` is set (`Analytics` class) |

## Dashboard

- **Last 3 minutes:** a ring where alerts sweep clockwise from the top as they age, one
  track per priority (safety outside, speech inside), live mic level in the centre.
  A hollow dot means the wristband was not connected when that alert fired.
- **Live / 1H / 24H / 7D / 30D:** alert counts stacked by priority over time, with the
  average mic level; long ranges read the server's hourly rollups.
- Alerts by type, a weekly rhythm heatmap (hour × weekday), the latest alerts, and
  each listener's live level and wristband link.
- Simulated demo data is flagged in the database and can be hidden with one click.

## Run it locally

You need the SpacetimeDB CLI (`curl -sSf https://install.spacetimedb.com | sh`) and Node.

```sh
# 1. Start a local SpacetimeDB server (leave it running)
spacetime start

# 2. Publish the module
cd analytics/spacetimedb && npm install
spacetime publish fortwatch --server local

# 3. Read the device key (only the database owner can read this table)
spacetime sql fortwatch --server local "SELECT ingest_key FROM config"

# 4. Run the listener with analytics on
export FORTWATCH_ANALYTICS_URL=http://localhost:3000/v1/database/fortwatch/route
export FORTWATCH_ANALYTICS_KEY=sk_...        # from step 3
.venv/bin/python live_demo/mac_listener.py   # prints "Analytics: on, as <hostname>"

# 5. Open the dashboard
cd analytics/dashboard && python3 -m http.server 8766
# http://localhost:8766/?server=http://localhost:3000
```

Optional demo data, so the charts have history before a real run:

```sh
spacetime call fortwatch --server local seed_demo '"sk_..."' 7 420      # 7 days; 420 = UTC offset in minutes (PDT)
spacetime call fortwatch --server local set_simulation '"sk_..."' true  # a live simulated listener
spacetime call fortwatch --server local clear_simulated '"sk_..."'      # remove all simulated data
```

To host it instead, publish to SpacetimeDB Maincloud (`spacetime login`, then
`spacetime publish <unique-name>`); the ingest URL becomes
`https://maincloud.spacetimedb.com/v1/database/<unique-name>/route`.

## HTTP API

All writes need the `x-device-key` header. Base: `<server>/v1/database/<db>/route`.

| Method | Path | Body |
|---|---|---|
| GET | `/health` | none |
| POST | `/alert` | `{"deviceId":"pedro-mac","event":"KNOCK","score":0.62,"level":54,"delivered":true,"atMs":1792890000000}` or `{"deviceId":"…","alerts":[…]}` (max 200, for alerts buffered offline) |
| POST | `/heartbeat` | `{"deviceId":"pedro-mac","name":"pedro-mac","level":37,"link":"ble","wristbandConnected":true}` |

The listener sends one heartbeat every 2 s and alerts as they happen. If the server is
unreachable it keeps up to 500 alerts and sends them later; it never delays the
wristband.

## Data

| Table | Public | Contents |
|---|---|---|
| `alert_event` | yes | One row per alert: event, label, priority (3 safety … 0 speech), score, level, delivered, time |
| `hourly_stat` | yes | Per-hour counts per event, kept by the server |
| `device` | yes | Each listener: live level, link, wristband connected, last seen |
| `config` | no | Device key, retention (90 days) |

## Changing the schema

Edit `spacetimedb/src/index.ts`, republish, then regenerate the bindings and rebuild the
page:

```sh
cd analytics/dashboard && npm install
npm run generate && npm run build
```

Republishing with a breaking schema change needs `--delete-data`, which **erases all
recorded alerts**.

## Limits

- Reads are public: anyone with the server address can see the alerts. Writes need the
  device key, a shared secret; keep it out of the repo.
- "Reached wristband" means the Bluetooth/USB link was connected when the alert was
  sent, not a confirmation that the wristband displayed it.
- Tested: the listener's uploader against a live server (stubbed audio), key
  rejection, offline buffering, and the dashboard with simulated data. **Not yet
  tested during a live microphone run with the wristband.**
